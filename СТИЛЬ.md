# СТИЛЬ

> **ПРОТОКОЛ 05 · ФИРМЕННЫЙ СТИЛЬ**

**Версия:** 1.0.0  
**Состояние:** 🟡 В развитии

Фирменный стиль GeraK нужен не для того, чтобы все проекты выглядели одинаково.

Он нужен для другого:

> **Чтобы разные проекты ощущались частью одной экосистемы.**

---

## 🎯 Характер GeraK

Базовая формула:

**технический + современный + живой + аккуратный + с характером**

| Характер | На практике |
|---|---|
| **Технический** | Точность, структура, настоящая инженерия |
| **Современный** | Чистая композиция и актуальный визуальный язык |
| **Живой** | Человек должен чувствовать, что проект развивается |
| **Аккуратный** | Никакого визуального шума ради визуального шума |
| **С характером** | Узнаваемость, собственный голос и немного юмора |

---

## 🧱 Главный принцип

GeraK не использует один шаблон для всех проектов.

Вместо этого используется **общий визуальный характер**.

~~~text
                    GeraK
                      │
        ┌─────────────┼─────────────┐
        │             │             │
     Lab           Store        Network
        │             │             │
   свой образ     свой образ    свой образ
        │             │             │
        └─────────────┼─────────────┘
                      │
              общий характер
~~~

> **Единый характер, не единая форма.**

---

## 🎨 Визуальный язык

Основные принципы:

- чистая композиция;
- заметная визуальная иерархия;
- достаточно свободного пространства;
- аккуратная сетка;
- современная типографика;
- ограниченное количество акцентных элементов;
- понятные статусы;
- визуальные схемы там, где они действительно объясняют содержание;
- изображения, которые помогают понять проект.

Хорошее оформление должно позволять быстро ответить:

**Что это?**  
**Зачем это нужно?**  
**Куда нажать, чтобы узнать больше?**

Если декоративный элемент не помогает ни одному из этих вопросов, он необязателен.

---

## 🌑 Светлая и тёмная подача

GeraK допускает как светлые, так и тёмные визуальные решения.

Важнее не конкретный цвет, а:

- контраст;
- читаемость;
- иерархия;
- узнаваемость;
- согласованность.

Тёмная подача особенно уместна для технических схем, лабораторных проектов, экспериментальных интерфейсов и протокольной символики.

Светлая подача хорошо подходит для документации, каталогов и информационных страниц.

Это рекомендации, а не обязательное правило.

---

## 🔷 Цвет

На уровне всей экосистемы не требуется единая палитра.

Собственные цветовые системы проектов допустимы.

Цвет должен выполнять функцию:

- выделять;
- группировать;
- обозначать состояние;
- создавать акцент;
- помогать навигации.

Не следует использовать десятки ярких цветов одновременно.

### Статусы

- 🟢 **Активен / актуален**
- 🟡 **В развитии / требует внимания**
- 🔵 **Информационный**
- 🔴 **Критический / важное ограничение**
- ⚪ **Архив / не развивается**

---

## ✍️ Типографика

Текст рассчитан прежде всего на чтение.

Приоритет:

1. заголовок;
2. краткое объяснение;
3. ключевая информация;
4. детали;
5. дополнительные материалы.

Для GitHub-документации предпочтительны:

- короткие абзацы;
- списки;
- таблицы;
- цитаты для важных принципов;
- Mermaid для связей и процессов;
- раскрывающиеся блоки, когда деталей становится много.

---

## 🖼️ Изображения

Изображение в GeraK должно иметь задачу.

Оно может:

- показать интерфейс;
- объяснить архитектуру;
- представить проект;
- передать атмосферу;
- помочь отличить проекты друг от друга.

Плохое изображение существует только потому, что README «должен иметь картинку».

### Фирменный символ

GeraKProtocol будет иметь собственный символ.

Он должен быть:

- узнаваемым в маленьком размере;
- простым;
- геометрически цельным;
- пригодным для SVG;
- пригодным для GitHub avatar;
- пригодным для README;
- пригодным для Social Preview;
- самостоятельным без обязательного текста.

Символ представляет **сам протокол и идею экосистемы**, а не конкретный проект.

## 🐙 GitHub как часть стиля

GitHub для GeraK является не просто хранилищем исходного кода.

Это часть публичного представления проектов.

### Репозиторий

- понятное название;
- короткое описание;
- актуальный README;
- корректные ссылки;
- понятный статус проекта.

### README

README должен быстро объяснять:

1. что это;
2. зачем это;
3. как это работает или используется;
4. где находятся дополнительные материалы.

Если проект сложнее одной страницы, подробности лучше выносить в отдельные документы.

### Social Preview

Для проектов, где визуальное представление имеет значение, рекомендуется собственная Social Preview.

Она должна быть узнаваемой, но не обязана повторять логотип проекта один в один.

---

## 🧭 Навигация

Документация GeraK должна быть связанной.

~~~text
README
  │
  ├── что это
  ├── как устроено
  ├── документация
  └── связанные проекты
             │
             ▼
        другой проект
             │
             ▼
           README
~~~

Каждый переход должен иметь понятную причину.

Не нужно создавать десятки ссылок просто ради плотности навигации.

---

## ✍️ Язык и тон

Основной язык GeraK — русский.

Текст должен быть:

- понятным;
- конкретным;
- современным;
- технически точным;
- спокойным;
- без лишней бюрократии.

Настоящие технические названия не нужно искусственно переводить:

GitHub, Swift, iOS, JSON, Python, Xcode, Git.

### Предпочтительный тон

Не:

> Настоящим документом устанавливается обязательный порядок функционирования программных компонентов...

А:

> Этот документ объясняет, как проект связан с остальной экосистемой.

GeraK говорит нормально.

## 🧪 Фирменный юмор

Юмор является частью характера GeraK.

Ориентир:

**примерно 10–15% характера, 85–90% содержания.**

Хороший пример:

> **Серьёзно к проектам. Не слишком серьёзно к себе.**

Ещё один:

> **На первый взгляд всё просто. Это хороший знак.**

Плохой вариант:

- шутка в каждом заголовке;
- мем вместо технического объяснения;
- намеренная нечитаемость;
- ирония там, где нужна точность.

> **Если шутка мешает понять документ, шутка проиграла.**

---

## 🧩 Индивидуальность проектов

Общий стиль не должен уничтожать характер конкретного проекта.

| Проект | Естественный образ |
|---|---|
| **GeraKLab** | Лаборатория, эксперименты, исследования |
| **GeraKStore** | Магазин, инфраструктура, каталог |
| **GeraKNetwork** | Сервис, сеть, техническая система |
| **GeraKWonderAlice** | Эксперимент, ИИ, умные устройства |

Это не жёсткие дизайнерские ограничения.

Проект может развить собственный образ, если он остаётся понятным и не противоречит общему характеру GeraK.

---

## 🚦 Сила стилевых правил

### 🔴 ОБЯЗАТЕЛЬНО

- корректное название проекта;
- ясное назначение;
- читаемая документация;
- честное описание связей;
- отсутствие намеренного визуального хаоса.

### 🟡 РЕКОМЕНДУЕТСЯ

- аккуратный README;
- визуальная иерархия;
- схемы;
- единый подход к статусам;
- качественные изображения;
- ссылки на связанные проекты.

### 🔵 ПО НЕОБХОДИМОСТИ

- Social Preview;
- дополнительные SVG;
- сложные Mermaid-схемы;
- отдельная брендовая палитра;
- анимации;
- дополнительные визуальные материалы.

---

## 🚫 Чего GeraK не делает

GeraK не требует:

- одинаковых логотипов;
- одной палитры для всех;
- одного UI;
- одного шрифта во всех приложениях;
- одинаковой структуры README;
- одинаковой архитектуры;
- одинакового уровня юмора.

Общность должна появляться естественно, а не через принуждение.

---

## 🔮 Стиль может развиваться

GeraKProtocol 1.0.0 фиксирует основу, а не замораживает дизайн навсегда.

По мере появления новых проектов могут появляться:

- новые визуальные приёмы;
- новые типы схем;
- новые способы представления проектов;
- новые элементы символики.

Если новый приём работает лучше старого, протокол может его принять.

> **Стиль должен сохранять характер, а не мешать развитию.**
